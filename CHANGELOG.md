# Changelog

All notable changes to The Marvellous Suspender are tracked in this file.

Format inspired by [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
The project adheres (pragmatically) to [Semantic Versioning](https://semver.org/).

Entries under "Unreleased" live on a feature branch until merged into `master`.

## [9.0.3] (Unreleased)

### Added
- **Separate auto-suspend timeout for battery power** (`gsStorage.js`, `options.html`, `options.js`, `style.css`, `tgs.js`, `gsUtils.js`, `gsTabSuspendManager.js`, `background.js`, all 18 `messages.json` locales, #252): new "Suspend tabs on battery power after" select shown side by side with the existing AC timeout (`gsTimeToSuspendOnBattery`, defaults to "Same as when plugged in", empty string, no override). When set to a specific value and the computer is currently unplugged, `resetAutoSuspendTimerForTab()` in `tgs.js` uses it instead of the normal timeout, lets tabs suspend more aggressively on battery without affecting the AC timeout, reusing the existing `navigator.getBattery()`/`tgs.isCharging()` plumbing already in place for the "never suspend while charging" option. The `battery.onchargingchange` listener in `background.js` now also resets all tabs' timers on a charge-state flip whenever a battery-specific timeout is set (previously it only did this for the "never suspend while charging" option), `gsUtils.js`'s per-tab settings-change handler resets a tab's timer when this option itself changes while on battery, and `checkTabEligibilityForSuspension()` in `gsTabSuspendManager.js` uses the same effective-timeout logic so a battery timeout still works even if the AC timeout is set to "Never". `isCharging()` can return `undefined` (not `false`) before the battery API's first read resolves or when it's unavailable in this MV3 service worker; every check here treats that as "unknown, don't override" rather than "on battery". `resetAutoSuspendTimerForAllTabs()` now clears only the per-tab suspension alarms instead of `chrome.alarms.clearAll()`, so a charge-state flip no longer wipes the unrelated auto-backup/retry/news-feed alarms.
- **Debug page: live power-source indicator** (`debug.html`, `debug.js`, `img/icons.svg`): new "power source" row in Controls shows a plug/battery icon and "AC power"/"on battery" text for the same `navigator.getBattery()` read the new battery-timeout option (above) and the existing "never suspend while charging" option rely on, updating live on `onchargingchange`, a quick way to confirm what the extension currently sees without guessing from behaviour alone. An equivalent indicator was first tried directly in Options next to the battery-timeout select, but ended up fighting that page's `.formRow > .topLabel { flex-basis: 100% }` layout rule for no real benefit; the debug page's existing icon+label+live-value row pattern (already used for the news feed status) fit it far better without any CSS wrestling.
- **"Always reopen suspended tabs scrolled to the top" option** (`gsStorage.js`, `options.html`, `options.js`, `tgs.js`, `contentscript.js`, all 18 `messages.json` locales, #308): new checkbox in Options → Suspended tabs (`gsDontRestoreScrollPos`, off by default) skips restoring the saved scroll position on unsuspend; the tab reopens at the top of the page instead of wherever it was scrolled to when suspended, with a tooltip explaining it applies to both automatic and manual suspension and overrides `#section` link anchors. Grouped with the other unsuspend-time behaviours (e.g. "unsuspend on focus") rather than the auto-suspend-trigger options above, since it's about what happens on reopen, not what triggers suspension. Implemented at `unsuspendTab()` in `tgs.js`, which sends an explicit `'top'` sentinel to `contentscript.js` when the option is on, forcing the scroll position to 0 even when the URL has a `#fragment` that would otherwise let the browser's native anchor-scroll override it.
- **Opt-in: reload also unsuspends background tabs** (`gsStorage.js`, `suspended.js`, `options.html`, `options.js`, all 18 `messages.json` locales, #158): the "reload to unsuspend" detection only ever counted a reload as an explicit user request when the reloaded tab was the currently focused one; reloading a suspended tab in the background (via Ctrl+R on a multi-tab selection, or right-click → Reload on an inactive tab) silently did nothing, since the tab's own `beforeunload` handler skipped recording the trigger for anything but the focused tab. New "Reload also unsuspends tabs in the background" checkbox in Options → General lifts that focus check when enabled (off by default, so nothing changes for existing users); doesn't touch Chrome's or TMS's own background-tab discarding logic, only whether a reload on such a tab gets recognized afterwards. Ships with an explanatory tooltip (all 18 locales) since the behaviour change is easy to miss from the label alone.
- **Drive auto-backup: PKCE + refresh_token replaces the implicit-flow fallback on Brave/Vivaldi** (`gsBackup.js`, `manifest.json`, #437): on browsers where `chrome.identity.getAuthToken()` doesn't work (Brave, Vivaldi), Drive auto-backup fell back to `launchWebAuthFlow()`'s implicit flow — a short-lived (~1h) access token, silently renewed via `launchWebAuthFlow({ prompt: 'none' })`. That renewal depends on the browser's ambient Google session for that tab, which isn't reliable on Brave/Vivaldi once the token expires, and was the reported cause of Drive accounts flipping to "disconnected" after just 1-2 automatic backups. The fallback now uses authorization-code + PKCE instead: a one-time interactive consent mints a long-lived `refresh_token` (`chrome.storage.local`), and every renewal after that is a direct POST to `oauth2.googleapis.com/token` — no tab, no cookies, no dependency on ambient browser session state. Reuses the existing "Web application" OAuth client (#420) rather than registering a new one, since Google's "Desktop app" client type (verified live against the authorize endpoint) rejects `chrome.identity.getRedirectURL()`'s `https://<ext-id>.chromiumapp.org/` redirect with `redirect_uri_mismatch` — that client type only accepts loopback/`urn:ietf` redirects. `manifest.json`'s `connect-src` gained `https://oauth2.googleapis.com` (previously only `www.googleapis.com`/`accounts.google.com` were allowed), without which the token-exchange `fetch()` failed silently. `src/js/gsOauthSecrets.js` is now a *committed* placeholder (`PKCE_CLIENT_SECRET = 'REPLACE_ME'`) rather than a gitignored file the static `import` could fail to find — a Codex review round caught that a missing import here failed the whole module and stopped the service worker from registering at all, for every user, not just ones touching Drive backup. A second review round then caught that the first fix (a lazy runtime `import()` instead) traded that bug for a worse one: MV3 service workers don't support dynamic `import()`, so the automatic, non-interactive token refresh — which runs in the service worker, unlike an interactive "Connect" click from `backup.html`'s own page context — would have silently failed every time, masked during manual testing because the interactive path never hit it. The real secret now lives only in a new gitignored `src/js/gsOauthSecrets.local.js`, and Grunt's build pipeline (`checkOauthSecrets` + a new `string-replace:oauthSecret` task) substitutes it into the *packaged build's own copy* of `gsOauthSecrets.js`, leaving the tracked placeholder untouched. **Migration note for existing Brave/Vivaldi users already connected via the old implicit flow**: no prior release could have stored a `refresh_token` for them, so once their current short-lived session expires (within about an hour of updating), the next automatic backup attempt fails and the extension flags the existing "Drive disconnected" badge — expected, unavoidable given Google requires interactive consent to mint a refresh token, and fixed with a single manual "Connect" click in Options → Backup, same as any other reconnect. Everyone reconnecting from that point on gets the new, more reliable renewal path with no further action needed. **Known, accepted limitation — the client secret ships inside the packaged extension**: a third review round pointed out that a "Web application" OAuth client's secret (the type used here) is, by Google's own classification, meant to stay confidential server-side — unlike "Chrome app"/"Desktop app"/mobile client types, which Google explicitly documents as *not* needing real secret confidentiality (installed apps can't keep a secret truly secret, so Google doesn't ask them to). This project's client can't use one of those exempted types instead: a "Chrome app" client only works with `chrome.identity.getAuthToken()` — the very API failing on Brave/Vivaldi that this whole fix exists to work around — and a "Desktop app" client rejects `launchWebAuthFlow()`'s `chromiumapp.org` redirect outright (verified live against Google's authorize endpoint). Since the extension package (CRX/ZIP) is trivially unpacked by anyone, this secret should be treated as effectively public once shipped. Accepted as a known limitation rather than standing up a separate backend service purely to broker this one exchange: a leaked secret only lets a third party register something that authenticates to Google *as this app* (e.g. a phishing consent screen impersonating it) — it does not expose any existing TMS user's Drive data, refresh token, or access token, since those never leave that user's own browser storage. Revisit if this ever needs hardening further. A fourth review round then caught two more, both in error-handling around the refresh token itself: `refreshAccessToken()` discarded the stored `refresh_token` on *any* 400/401 from the token endpoint, but a 400/401 doesn't only mean the token itself is dead (`invalid_grant`) — it can also mean a client-level failure like `invalid_client` (e.g. while the OAuth secret is mid-rotation) that has nothing to do with that specific token's validity; discarding it there forces every affected user through a fresh consent screen once the client itself is fixed, for a token that was never actually the problem. `exchangeTokenEndpoint()` now exposes the parsed `error` field on the thrown error, and only `invalid_grant` triggers the discard. Separately, `revokeAuthToken()`'s Drive "Disconnect" button ignored the revoke `fetch()`'s response entirely and cleared the local `refresh_token` regardless of outcome — if the revoke call failed (blocked network, a transient 5xx), the long-lived grant stayed fully active server-side with no local token left to ever retry revoking it, silently leaving the account "disconnected" in the extension's UI while still authorized on Google's side. `revokeAuthToken()` now only clears local state when the revoke call actually succeeds (or Google reports the token already invalid via a 400, which is equivalent to done); on any other failure it throws instead, and `backup.js`'s disconnect handler surfaces that as a status message instead of silently reporting success — reusing the existing `js_options_backup_drive_auth_error` string (already translated in all 18 locales via Crowdin) rather than a new dedicated key, since a new key was first added only to en/it and a later review round caught it would render as an empty string in every other locale until the next Crowdin sync. A fifth review round then flagged that `checkOauthSecrets` now makes `grunt`/`npm run build` fail hard for anyone without the maintainer's private OAuth secret, even for a contributor who just wants a local zip/crx build with no interest in Drive at all. Deliberately left as-is rather than downgrading to a warning: `crx:private` a few steps later in the same task list already has the identical shape of requirement — a gitignored `key.pem` signing key, equally maintainer-only — so this doesn't introduce a new class of "can't build without a project secret" problem, only a second instance of an existing, accepted one specific to this repo's release tooling. It doesn't affect testing the PKCE flow itself, either: "Load unpacked" straight from `src/` never invokes Grunt, and anyone can still create their own `gsOauthSecrets.local.js` locally to test that path (see `gsOauthSecrets.example.js`) without ever running `grunt`.
- **"What's new" changelog modal on the Settings page** (`gsChangelog.js`, `gsStorage.js`, `options.html`, `options.js`, `style.css`, `Gruntfile.js`, all 18 `messages.json` locales): after an update, opening Settings now shows a one-time modal with just the current version's entries from this file (not the whole history), parsed client-side with a small regex-based markdown-to-DOM renderer (no `innerHTML`, so the source can't inject markup). Shown once per version (`gsLastSeenChangelogVersion` in `chrome.storage.local`), skipped entirely on a brand-new install. `CHANGELOG.md` lives at the repo root as usual; a `src/CHANGELOG.md` symlink keeps it available for local "Load unpacked" testing, and a dedicated Grunt copy step ships a real (dereferenced) copy inside the packaged extension.
- **Debug page: "reset changelog seen flag" action** (`debug.html`, `debug.js`): clears `gsLastSeenChangelogVersion` so the new changelog modal above can be re-tested from an unpacked/dev install without bumping the manifest version each time; a normal `Load unpacked` reinstall always sets the "first time" flag, which intentionally skips the modal, so there was no other way to re-trigger it locally.
- **Debug page: "repair favicons now" action** (`debug.html`, `debug.js`, `background.js`, `gsSession.js`, `suspended.js`, #449): "Clear favicon cache" only empties the cache; it doesn't force a re-check of currently open suspended tabs, so anyone needing an on-demand repair (session restore after a crash, "continue where you left off", or pre-9.0.2 installs without #397's startup-sentinel fallback) had no option short of restarting the browser again or unsuspending everything. The new action reuses `gsSession.performTabChecks()` (already decoupled from `runStartupChecks()`'s crash-recovery/version-branching logic) against the currently open tabs on demand, routed through the service worker like the existing `setCaptureLogs`/`clearLogs` actions since `gsTabCheckManager`'s check queue only exists there. Surfaced a pre-existing bug while wiring the response up: `chrome.runtime.sendMessage` with no `tabId` broadcasts to every extension page, not just the service worker, and every open `suspended.html`'s message listener was resolving `true` for actions it didn't even handle (an async function listener always returns a Promise regardless of its internal logic), racing against, and sometimes beating, the real response and turning the reported repair counts into `undefined`/`undefined`. `suspended.js` now dispatches synchronously against a known-actions list first, returning a real `false` for anything it doesn't own so it stops shadowing other listeners' responses.
- **Suspend/unsuspend all tabs in a tab group** (`tgs.js`, `background.js`, `manifest.json`, all 18 `messages.json` locales, #133): new context menu items "Suspend/Unsuspend all tabs in this group", both in the page context menu and in the tab-strip (right-click on tab) menu, plus two bindable keyboard shortcuts (`2c-suspend-tab-group`, `2d-unsuspend-tab-group`). Both act on every tab sharing the clicked/active tab's `groupId` and route through the standard suspend queue, so whitelist, form-input, and audible-tab protections apply as usual; on an ungrouped tab they are a no-op. The four new strings were translated by hand for all 16 non-English/Italian locales (reusing each locale's existing suspend/unsuspend and "all tabs in this window" phrasing) rather than left for the next Crowdin sync, so `npm run check-locales` stays clean.

### Fixed
- **`chrome.tabs.onUpdated`'s listener did real work (logging, a storage read, dispatching into both suspended/unsuspended tab handlers) for every tab-state change, including ones it never acts on — chiefly `'frozen'`, which live testing found Chrome flips on/off across background/suspended tabs constantly (over 4000 occurrences in a 43-minute session, with dense clusters of dozens within a few seconds)** (`background.js`): every one of those irrelevant events still reached `gsUtils.log()` (a real cost with `captureLogs` on: buffering, coalescing, periodic storage flushes) and both `tgs.handleSuspendedTabStateChanged()`/`handleUnsuspendedTabStateChanged()`, only for either to immediately discover there was nothing to do (both already early-return for a `changeInfo` without `status`/`discarded`/`audible`/`pinned`, which a `frozen`-only event never has). The listener now checks for one of those actually-relevant keys before doing anything at all, cutting logging and dispatch overhead entirely for events nothing here has ever acted on. Confirmed live via debug reports tying repeated Out-of-Memory crashes to dense `frozen` clusters (up to 39 within a few seconds) — this alone may not fully explain a crash at that scale, but removes real, previously-unnecessary load from every one of the thousands of these events in a typical session.
- **A burst of suspended tabs completing near-simultaneously (e.g. Chrome un-discarding several at once when a window regains focus after being idle) could crash the extension with an out-of-memory error, unrelated to session restore itself** (`tgs.js`): `chrome.tabs.onUpdated`'s `'complete'` handler calls `initialiseSuspendedTab()` independently for every tab, with no throttling — each call did its own storage reads, a `chrome.tabs.sendMessage()` (with up to ~6s of retries) to the tab's content script, and a `gsTabCheckManager` queue enqueue, all unbounded. Confirmed live via a genuine "Out of memory" crash (Chrome's own error page, not a caught exception — nothing in the extension's log buffer past the last normal entry) tied to a burst of 15-20 suspended tabs all firing `'complete'` within roughly 130ms of each other on window-focus regain, distinct from the already-bounded session-restore path (which staggers tab creation and was confirmed unaffected: a 47-tab restore completed cleanly in ~3.3s with every tab correctly recreated as a lightweight suspended placeholder, none as a real page load). `initialiseSuspendedTab()`'s actual work (message send + queue enqueue, not the explicit "reload to unsuspend" path, which stays instant) is now capped at 5 concurrent, so a burst like this gets spread out over time instead of firing every tab's full init work in the same instant. A larger, live reproduction of the same crash (46 tabs this time, not 15-20) then showed this concurrency cap barely helped: the actual memory- and IndexedDB-heavy work (favicon lookup, title/theme setup) runs inside *each suspended tab's own separate page context*, driven by the `'initTab'` message this function sends — `chrome.tabs.sendMessage()` resolves as soon as that page's own listener acknowledges it, a few ms, long before that page's own async work is actually done. Capping how many sends are *in flight* at once barely changes how many separate tab contexts end up doing real work at the same time, since each send-and-acknowledge round trip here was already fast regardless of the receiving page's own workload. Replaced with an actual dispatch-rate limiter: at most 5 tabs are sent their `'initTab'` message per 300ms, regardless of how fast those sends themselves resolve, spreading a 46-tab burst over several seconds of real wall-clock time instead of firing it almost all at once. A Codex review round then caught that this rate limiter didn't actually limit anything: it used "queue is non-empty" as the signal for whether a cooldown window was still needed, but a burst arriving as separate `chrome.tabs.onUpdated` events (not one synchronous batch) drained the queue back to empty after every single arrival, so the cooldown timer never armed and every call slipped through immediately regardless of the limiter. Replaced with a window counter that persists across `pump()` calls independent of queue state, so arrivals spread out one at a time are still correctly capped. A further Codex review round then caught that the underlying premise for this fixed-interval design was itself wrong: it assumed `chrome.tabs.sendMessage()` for `'initTab'` resolved almost instantly regardless of the receiving page's own work, so a batch released purely on elapsed time could still leave an unbounded number of tabs genuinely in flight at once whenever any single tab's real work outlasted the 300ms interval. Reading `suspended.js`'s own `handleMessageRequest()` directly (rather than inferring from log timing, which is what led to the wrong premise in the first place) confirms `sendResponse()` is only called *after* `await initTab(...)` completes — the message genuinely blocks on the real favicon/title/theme work finishing, not a quick acknowledgement. Reverted to a real concurrency bound: a job's slot is held for its actual duration and only released once the real work resolves, capping genuinely concurrent in-flight jobs at 5 rather than releasing a new batch on a fixed timer regardless of whether the previous one had actually finished. A further Codex review round then caught that a tab closing or navigating away while still *waiting* for one of those 5 slots (not yet started) stayed queued anyway — when its turn eventually came, it would still run the full `sendInitTabMessageWithRetry()` cycle (~6s of retries) against a tab that no longer existed, occupying a slot the whole time and delaying real, still-open tabs queued behind it; in a large burst, enough stale entries at the front could delay valid work for minutes, or leave it uninitialised entirely if the service worker recycled in the meantime. Queued entries are now tracked by tab ID, and `chrome.tabs.onRemoved` (already wired to `removeTabIdReferences()`) cancels any still-queued entry for that tab immediately instead of letting it consume a slot for no reason. A final Codex review round caught the remaining gap: an in-place navigation on a still-queued tab (an unsuspend command, address-bar entry) fires neither `onRemoved` nor `onReplaced`, so that cancellation path never triggers, and the stale entry would eventually send its old `'initTab'` payload to the new page (no receiver for it) while still occupying a slot for the full retry budget. `_runInitSuspendedTabLimited()` now cancels any existing queued entry for the same tab ID before enqueuing a fresh one, so a tab re-entering this path before its previous entry ever started always replaces it instead of leaving both around. A further Codex review round caught the remaining gap in the opposite direction: a tab unsuspending, or navigating away, while still queued for a slot doesn't re-enter this path at all — it routes to `handleUnsuspendedTabStateChanged()` instead once `gsUtils.isSuspendedTab(tab)` reads false, and neither `onRemoved` nor `onReplaced` fires for an in-place transition, so the stale entry was never cancelled. `handleUnsuspendedTabStateChanged()` now unconditionally cancels any queued entry for that tab ID itself — reaching that handler at all is already proof the tab is no longer suspended. Yet another Codex review round caught that this still missed one path: `background.js`'s dispatch only calls `handleUnsuspendedTabStateChanged()` when `gsUtils.isNormalTab(tab)` also passes, so a queued tab navigating to a "special" URL (`chrome://`, another extension's page) that `isNormalTab()` excludes fell through both handler branches entirely, skipping cancellation altogether. The cancellation call moved out of `handleUnsuspendedTabStateChanged()` and into `background.js`'s dispatch itself (a newly exported `tgs.cancelQueuedInitSuspendedTab()`), called unconditionally whenever `isSuspendedTab(tab)` reads false — covering the normal-tab and special-page cases alike. Still another Codex review round caught a narrower race none of the above touches: `initialiseSuspendedTab()` awaits several session-storage reads *before* ever calling `_runInitSuspendedTabLimited()` — if the tab navigates away during that window, the transition's cancellation call runs while no queue entry exists yet to remove, and the stale entry gets enqueued anyway once those awaits finish. `_runInitSuspendedTabLimited()`'s `run()` now re-fetches the tab and re-checks `gsUtils.isSuspendedTab()` immediately before starting the real work (covering both the "runs immediately" and "was queued, runs later" paths), instead of only ever checking at enqueue time.
- **`checkQueue`'s own responsiveness check could throw an uncaught exception, stranding one of its (deliberately few) concurrent slots for up to 60 seconds instead of failing promptly** (`gsTabCheckManager.js`, `gsTabQueue.js`): confirmed live via the extension's own error console — `chrome.tabs.sendMessage(tab.id, { action: 'getSuspendInfo', tab })` in `checkSuspendedTab()` can resolve successfully with `undefined` instead of rejecting (e.g. if the tab navigates/reloads in the narrow window between the message arriving and `sendResponse()` being called), and the very next line read `suspendInfo.sessionId` with no guard, throwing `Cannot read properties of undefined`. Worse, `gsTabQueue.js`'s `processTab()` called its `executorFn` (the function that threw) with no `try`/`catch` at all — explicitly commented `// async. unhandled promise` — so the failure never reached anything that could resolve, reject, or requeue the job; the slot just sat in `STATUS_IN_PROGRESS` until the job's own `jobTimeout` (60s default) eventually fired via a separate timer. With only 3 concurrent executors on this queue, repeated occurrences could meaningfully choke its real throughput for extended periods. Both gaps are now closed: `checkSuspendedTab()` guards against an empty `suspendInfo` and requeues promptly (same as the already-handled rejection case just above it), and `processTab()`'s `executorFn`/`exceptionFn` calls are now wrapped so any unexpected throw fails the job immediately instead of waiting out the full timeout. A Codex review round then caught that the initial version of this fix rejected the job directly on an unexpected throw, rather than routing it through the queue's own configured `exceptionFn` (the same one the timeout path already uses, which resolves `false` rather than rejecting) — a caller aggregating many of these jobs via `Promise.all()`, like `performInitialisationTabChecks()` at startup, would have the whole aggregate abort on one queue-internal failure, skipping that caller's own post-await cleanup (removing its temporary listener, restoring queue properties) and potentially leaving startup permanently stuck in "initialising" state. Both the executor-throw and exceptionFn-throw paths now route through the same caller-safe `resolve(false)` contract instead.
- **A single suspended tab with a large-resolution favicon (e.g. a site serving a 512×512 apple-touch-icon as-is) could push V8's shared per-process memory allocator toward its hard ~4GB cap, crashing the whole browser process once enough suspended tabs piled up in it** (`gsFavicon.js`, `gsUtils.js`): confirmed via a real, reproducible crash — Crashpad's local minidump for a "V8 fatal error: Out of Memory" showed `view-count`/`web-frame-count`: 49, all sharing one origin (`chrome-extension://…`), since Chrome puts every same-origin extension page (every open `suspended.html` is the same origin) in one shared renderer process with one shared V8 heap. The dump's `v8-oom-old-space-size` (regular JS objects, including the log buffer) was a tiny 18MB, while `v8-oom-memory-allocator-size` (external/backing-store memory: canvas pixel buffers, typed arrays) sat at 3.7GB of a 4.2GB cap — the smoking gun pointing at binary image data, not logging. `gsFavicon.js`'s `buildFaviconMeta()` sized its working canvas to the source image's *native* resolution before calling `getImageData()`, allocating two full-size `Uint8ClampedArray` copies and two `toDataURL()` PNG encodes — cost that scales with the source image's pixel count, even though the result (`suspended.js`'s `setFaviconMeta()`) is only ever shown as a tiny tab-bar icon. That per-tab cost multiplies across every suspended tab sharing the same renderer process. The working canvas is now capped to a 128px max dimension (downscaled via `drawImage()`, same pattern the file's other, already-capped `createImageFingerprint()` uses), bounding the cost regardless of the source image's actual resolution. Separately, `gsUtils.js`'s log-buffer merge (`_mergeAndPersistCore()`, added in #464-#467) re-sorted the *entire* persisted buffer (up to `_LOG_BUFFER_FULL_MAX` = 10,000 entries) on every single merge, even though it's typically already sorted and only a small new batch is being appended — real, avoidable CPU/allocation churn on every flush with `captureLogs` on. A new `_appendSorted()` helper skips the full-array sort whenever the new batch's timestamps already sort after the existing buffer's (the common case), falling back to a full sort only for the rare genuinely out-of-order merge. A Codex review round then caught that the cap alone left every already-suspended tab exposed indefinitely: `getFaviconMetaFromCache()` returns an IndexedDB-persisted `faviconMeta` as-is, only fingerprint-validating it, with no check on its dimensions — so profiles that had already accumulated an oversized favicon (precisely the ones most likely to have triggered the crash) would keep decoding it at native resolution in every suspended tab even after updating. A new `FAVICON_META_VERSION` stamped onto every freshly-built `faviconMeta` and checked in `isFaviconMetaValid()` makes any pre-existing cache entry (built before this cap existed) read as invalid, so it falls through the normal cache-miss path and gets rebuilt — and re-saved — with the new capped logic, self-healing existing profiles over time as suspended tabs are naturally revisited.
- **Debug page: tabs whose content script stopped responding (page still alive, distinct from a discarded tab) stayed stuck reporting "unknown" indefinitely, surviving repeated page reloads** (`debug.js`): `getDebugInfo()` probed a "normal" tab's content script directly via `sendRequestInfoToContentScript()`, and on failure fed a `null` status into `calculateTabStatus()`, which *itself* attempted the exact same probe a second time — pure wasted duplicate work — before falling back to `STATUS_UNKNOWN` on a second failure, with no attempt to reinject the content script. Only `tgs.js`'s own periodic `checkQueue` responsiveness checks ever did that reinjection, entirely independent of this page, so a tab that broke between two of those scheduled runs had no way to recover via the debug page at all; confirmed via live testing, several tabs stuck reporting "unknown" for many minutes across repeated manual reloads. `getDebugInfo()` now routes the check through `gsTabCheckManager.queueTabCheckAsPromise()` — the same responsiveness-check queue `checkQueue` itself uses, reinjection attempt included — instead of a one-shot probe, and `calculateTabStatus()` no longer needs its own redundant attempt, since it's given the already-resolved status directly. Every page (including this one) gets its own separate `gsTabCheckManager` module instance, so `debug.js` now also calls `gsTabCheckManager.initAsPromised()` during its own init (the same pattern `health.js` already used for its own tab-suspend/check needs) — without it, `queueTabCheckAsPromise()` would silently hit the "queue not initialized" guard and resolve `STATUS_UNKNOWN` immediately every time, skipping the reinjection attempt entirely. A Codex review round then caught that the recovery still wasn't visible where it mattered: a tab needing actual reinjection routinely takes longer than the 500ms per-tab render deadline `fetchTabInfo()` already enforces, so that render still (correctly) shows "unknown" for it — but the late result, once it did arrive, was simply discarded, since only the raced `promiseWithTimeout()` value ever reached the table. The row stayed stuck showing the timeout fallback until some unrelated later refresh happened to run. Each tab's `<tr>` now carries a `data-tab-id` attribute, and the underlying (unraced) info promise patches that one row in place once it resolves, so a tab that recovers mid-check updates live instead of waiting for the next full profiler refresh. A further Codex review round caught two more, both real races the live-update fix above introduced. First: a late update from an *older* pass could overwrite a *newer* pass's already-correct row for the same tab (e.g. it genuinely became pinned in between) with stale data, since nothing tracked which pass a given row's data actually came from; every pass now stamps a generation counter, and a late update only applies if its own pass is still the newest one. Second, and more serious architecturally: this page's own separate `gsTabCheckManager` instance (`initAsPromised()`'d locally, added above) has no visibility into a recovery the *service worker's own* queue might already be running for the same tab (e.g. `tgs.js`'s `handleTabFocusChanged()`) — two independent queues could both decide to reinject the same tab's content script at once, and reinjection is already documented (`gsTabCheckManager.js`'s own comments) as leaving old runtime listeners active when that happens. The check is now routed through a new `checkTabResponsiveness` message, handled in `background.js` by calling the service worker's own singleton `gsTabCheckManager` queue instead — the same one everything else in the extension already funnels through — and `debug.js` no longer creates (or initialises) its own separate instance at all. A final Codex review round caught that the new `checkTabResponsiveness` message wasn't marked service-worker-only: `chrome.runtime.sendMessage` with no `tabId` broadcasts to every open extension page, so `options.html`/`updated.html`'s own listeners (which didn't know this new action, unlike `background.js`) could resolve first with an unhandled-message response, racing and beating the service worker's real, slower one — leaving `calculateTabStatus()` falling back to the old one-shot probe with the background-queued recovery no longer attached to the live row update. Added `checkTabResponsiveness` to the existing `gsUtils.INTERNAL_MESSAGE_ACTIONS` set every page's `messageRequestListener` already consults for exactly this class of problem.

  On top of the review-driven fixes above, both `fetchTabInfo()` and `buildReport()` fired their whole per-tab batch via a plain `Promise.all(tabs.map(...))`, with no cap on how many ran at once — fine for a handful of tabs, but a profile with hundreds of them open would fire hundreds of concurrent `chrome.tabs.get()`/`chrome.alarms.get()` calls, and (for every "normal" tab) hundreds of simultaneous `checkTabResponsiveness` messages to the service worker, all in one instant, on every single profiler refresh or report generation. A new `mapWithConcurrency()` helper caps both to at most 20 tabs in flight at once, spreading that same total work out over time instead of bursting it — the debug page (and this whole log-buffer/tab-check machinery it now exercises) should stay usable rather than becoming the thing that finally tips a heavily-loaded profile (hundreds of tabs open) into crashing.

  A Codex review round then caught two consequences of that same batching change. First, in `fetchTabInfo()`: with concurrency-limited batches, a tab's real result can now land in the gap between "no row exists yet" (the initial render hasn't happened) and "the final render already ran" — the live per-row patch is a silent no-op in that gap, and without also tracking the fresher value elsewhere, the eventual render still baked in that tab's stale timeout fallback despite already knowing better. `debugInfos` is now populated in place from the same unraced result the live patch already uses, so the final render always reflects whichever is freshest. Second, in `buildReport()`: the service worker's own `gsTabCheckManager` queue has only 3 concurrent executors, so with more than a handful of "normal" tabs, the existing 500ms per-tab deadline expired for most of them well before the queue even got to processing them — not because they were unresponsive, but because they were still waiting their turn — and unlike the live table, a generated report has no later-refresh path to correct a wrong "unknown" afterwards; it freezes whatever it captured permanently. Report generation dropped the per-tab timeout entirely (the queue's own 60s job timeout is still the real upper bound) — it's a deliberate one-off action, unlike the live table, so it's fine for it to take longer in exchange for actually being correct.

Each one kicked off its own full `fetchTabInfo()` run, and every one of those calls `getDebugInfo()` — including a real `sendRequestInfoToContentScript()` round trip for every "normal" (non-suspended) tab — for every currently open tab again, all overlapping. On the very first load of a profile with more than a handful of slow "normal" tabs, this could leave the whole profiler table (and page controls) blank and inert for many seconds. - **Log buffer: a burst of near-simultaneous flushes from many open contexts (e.g. every suspended tab reacting to `captureLogs` being toggled) could make the whole extension sluggish, including unrelated page loads** (`gsUtils.js`): every `gsAppendLogEntries` message costs one full get+parse+stringify+set of the entire shared buffer (up to `_LOG_BUFFER_FULL_MAX` entries) — `chrome.storage.local` has no append primitive, only whole-value writes. A broadcast every open context reacts to at once (toggling `captureLogs` itself, which every suspended tab logs as "ignoring unhandled message") could land dozens of these messages within a few milliseconds of each other; merging each one separately serialized dozens of full-buffer round trips back to back through `_writeQueue`, each one's synchronous JSON work blocking this single-threaded context in turn — including its ability to promptly respond to anything else, like whatever `options.html`/`debug.html` needed from it on their own load. Confirmed via live testing with ~50 suspended tabs open and `captureLogs` on: reopening the debug/options pages became noticeably slow, worse than before this rework began. Incoming messages are now coalesced into one merge per 250ms window instead of one per message, turning a 50-tab burst into a single round trip; the live/report buffer size caps (`_LOG_BUFFER_MAX`/`_LOG_BUFFER_FULL_MAX`) are left unchanged, since a user with many tabs open is exactly the case where a shorter history would hurt diagnosing an issue the most — the coalescing alone removes the multiplier, independent of buffer size. A GitHub Codex review round then caught a severe regression the coalescing itself introduced: if many contexts had each independently accumulated up to their own `_pendingEntries` cap (5,000) while the service worker was unreachable, all flushing once it came back reachable could aggregate well over 100,000 entries into a single coalesced batch — and `_mergeAndPersistCore()` appended it via `current.push(...freshEntries)`, a variadic spread that turns every element into its own function argument and throws a `RangeError` in V8 past a few tens of thousands of them. Fixed two ways: `_mergeAndPersistCore()` now appends via `concat()`, which has no argument-count limit regardless of array size, and `_flushIncomingBatch()` now trims the aggregated batch itself down to `_LOG_BUFFER_FULL_MAX` (keeping the newest) before it's ever merged, since carrying more of it into the merge than the persisted buffer could retain anyway was pure waste. A local adversarial-review round then flagged that trimming only at flush time still let the aggregate grow unbounded, even if briefly, throughout the whole 250ms window while messages keep arriving — the exact CPU/memory spike this coalescing exists to avoid, just delayed a beat. `_incomingBatch` is now capped on every single arrival (not just once before merging), and appended via `concat()` rather than a spread there too, since a single sender's own entries array can already be large enough (up to its own 5,000-entry cap) to risk the same argument-count limit on its own. Another GitHub Codex review round then caught an ordering race the coalescing design introduced: the service worker's own logging (`error()` in particular, which flushes immediately and bypasses the incoming-message coalescing entirely) merges through `_mergeAndPersistCore()` via a separate call path from a page's coalesced batch, and both end up serialized by `_writeQueue` in whichever order they happened to be *called*, not the order their entries were actually logged in — a page's batch that had been waiting out its 250ms window could land after a genuinely newer service-worker-local error, and since the buffers trim from the front assuming it holds the oldest entries, that trim could then evict the newer error instead of the older batch. Both buffers are now re-sorted by `ts` after merging and before trimming, so the front is guaranteed to be chronologically oldest regardless of which call path landed first. Yet another GitHub Codex review round then caught that the two earlier, pre-merge trims (capping `_incomingBatch` on arrival, and again before it's handed to the merge) still trimmed by arrival order rather than `ts` — a backlogged context that reconnects last, contributing older entries, could evict another context's genuinely newer entries before they ever reached the sort-then-trim inside `_mergeAndPersistCore()`, permanently losing them (every sender still gets acknowledged with success, since nothing detects the loss). Both pre-merge trims now go through a shared `_keepNewestByTs()` helper that sorts by `ts` before keeping the newest, the same rule the merge itself now applies.
- **Log buffer: unbounded in-memory growth with `captureLogs` left on, plus a genuine memory leak when the service worker stays unreachable** (`gsUtils.js`): every page (including every open suspended tab) ran its own copy of `gsUtils.js` and, on every single log call, pushed the entry into two in-memory arrays capped at 500/10,000 entries — but `debug.js`'s live view and downloadable report both read straight from `chrome.storage.local` instead, and the two exported accessors for those arrays (`getLogBuffer()`/`getLogBufferFull()`) had no callers anywhere in the codebase. Dead weight: every context, including every suspended tab, could end up holding up to 10,000 duplicated log-entry objects in memory that nothing ever read, for as long as `captureLogs` stayed on. Removed both arrays and their accessors entirely; only `_pendingEntries` (the small, normally-empty-within-1.5s delta awaiting its next flush) remains per context. Separately, and more seriously: `_pendingEntries` itself had no upper bound — if the service worker (or `chrome.runtime` in a page context) stayed unreachable, every failed flush requeued its batch while new log calls kept appending more, with nothing ever shrinking it, so heavy logging in that state could grow it without limit until Chrome killed the page or the extension itself for memory pressure, matching a real "insufficient memory, extension disabled, needs reload" report. `_pendingEntries` is now capped at 5,000 entries, oldest dropped first, at every point it can grow (a new log call, or a failed flush requeuing its batch). A Codex review round then caught that the cap could trim the wrong half: `gsUtils.error()` calls `_flushNow()` immediately, bypassing `_scheduleFlush()`'s "only one timer pending" guard, so an error-triggered flush can overlap with an already in-flight scheduled one; their requeue-on-failure steps could then complete in either order, and since `unshift()` always lands at the front regardless of which batch is actually older, the cap's front-trim (which assumes the front is the oldest entries) could end up discarding more recent diagnostics while keeping stale ones. `_flushNow()` now chains every call through one promise (the same pattern `gsUtils.js`'s own `_writeQueue` already uses for the service worker's storage writes), guaranteeing one flush's requeue fully lands before the next one starts. A local adversarial-review round then caught that the entry-count cap alone doesn't bound memory: `_capPendingEntries()` limits how many entries can pile up, but not how large any single one is — a call site logging a large non-data-URL string or object repeatedly (`_redactDataUrls()` only catches `data:` URLs) could still push significant memory through even a handful of entries. `_appendEntry()` now truncates any single message past 4,000 characters (marked as truncated, with the original length noted) before it's ever buffered, bounding each entry's own footprint independently of how many of them exist.

The persisted `captureLogs` flag was restored only in `background.js`, so `gsChangelog.js`'s diagnostic `gsUtils.warning()` calls (added specifically to make changelog-modal failures diagnosable) never buffered anything running in `options.js`'s context, since that context's own `captureLogs` copy never got restored; and toggling captureLogs on the debug page only messaged the service worker, so an already-open page kept whatever value it loaded with. Fixing those two surfaced the deepest issue: with multiple contexts actually flushing now, each one overwrote storage with its own full local snapshot (or, in an intermediate append-merge attempt, still raced another context's uncoordinated read-modify-write), so two contexts logging around the same time could silently erase what the other had just written, and chrome.storage has no compare-and-swap to fix that with more retries. Settled on a single-writer design instead: only the service worker (`_isServiceWorker`, detected via `self instanceof ServiceWorkerGlobalScope`) ever touches these two storage keys; every other context hands its pending entries to it via a `gsAppendLogEntries` runtime message instead of writing directly. Inside the service worker, every write (a merge or a clear) is chained through one `_writeQueue` promise, so its own scheduled flush and an incoming message can no longer interleave their storage round trips either. `clearLogBuffer()` (only ever called from the service worker) now goes through that same queue, so it's correctly ordered against anything already merged or in flight instead of racing it. The `captureLogs` restore moved into `gsUtils.js` itself so every context picks up the persisted value on load, and a `chrome.storage.onChanged` listener there keeps it in sync live afterward, no per-page wiring needed for either. A fourth round then caught a self-sustaining loop the single-writer message actually introduced: `chrome.runtime.sendMessage` with no `tabId` broadcasts to every page, so every open suspended tab's (and `options.js`'s and `updated.js`'s) own message listener received the new `gsAppendLogEntries` action too, logged it as unhandled, and that log entry itself needed flushing via another broadcast, without end. Every page listener (plus `background.js`'s own separate one, which also received the broadcast alongside `gsUtils.js`'s dedicated handler for it) now silently ignores `gsAppendLogEntries` and `clearLogs` via a shared `gsUtils.INTERNAL_MESSAGE_ACTIONS` set instead of logging them as unhandled. That round also flagged that `manifest.json` declares `"incognito": "split"`, so a regular and an incognito window each run a fully independent service worker with its own `_writeQueue`, sharing the same storage but unaware of each other, defeating the "single writer" assumption for that one supported case; `_mergeAndPersist()` now stamps a `gsLogBufferVersion` counter on every write and re-checks it immediately after, retrying the merge (up to 5 attempts) on top of whatever the other worker just wrote if it changed underneath. A fifth round then caught that the counter itself couldn't actually prove which worker's write had landed: two workers racing off the same prior value both compute the same next number, so whichever `set()` happens to land last leaves a value both sides' verification reads back as a match, even though only one worker's batch is actually still in the buffers, silently losing the other one. Replaced the incrementing counter with a random per-attempt token (`crypto.randomUUID()`), so a worker's verification read now checks for its own exact token rather than a number any concurrent writer could equally have produced; a mismatch unambiguously means someone else's write landed, at which point the retry reads that fresh state and reapplies the batch on top of it. The same round (via a local adversarial review alongside GitHub's) then flagged the edge case a previous round had deliberately left as a disclosed limitation instead of engineering away: a page's batch already grabbed from its own `_pendingEntries` (or still mid-flight) at the exact moment "Clear log" runs could still land, and get persisted, right after the clear completed, resurrecting the entries the user just wiped — cancelling a message already in transit isn't something the extension messaging API offers a hook for. `_clearPersisted()` now also writes a `gsLogBufferClearedAt` timestamp (never removed by the clear itself), and every merge attempt drops entries older than it before persisting, regardless of which side of the clear the merge physically lands on. The same round also caught that a batch failing to persist after all 5 version-conflict retries, or a service worker unreachable mid-flight, silently discarded that diagnostic history for good; `_flushNow()` now requeues a failed batch at the front of `_pendingEntries` and lets the next scheduled flush retry it instead of losing it. A sixth round caught three more: `background.js`'s `messageRequestListener` was still declared `async` at the top (a separate instance of the same "async listener returns a Promise instead of the literal `true`/`false` Chrome needs" issue as elsewhere in this rework), so its early, synchronous-looking `return false;` for `gsAppendLogEntries` was actually wrapped in a Promise that could resolve before `gsUtils.js`'s own dedicated (and slower, since it does real storage I/O) listener responded; the sender keeps only whichever response arrives first, so `_flushNow()` could see that stray `false`, requeue an already-successfully-persisted batch, and resend (and re-persist) it every 1.5s indefinitely. `messageRequestListener` is now a synchronous function that returns `true`/`false` for real, running its async body in an internal IIFE. Second, the new `gsLogBufferClearedAt` cutoff only filtered the entries being merged, not the buffer state they were merged onto: if a merge's `get()` landed between Clear's two writes (the timestamp, then the buffer removal), it would still read the pre-clear buffer, and if its own `set()` then landed after Clear's removal, it silently reintroduced that entire pre-clear buffer while still verifying its own write as successful. `_mergeAndPersist()` now also re-checks `gsLogBufferClearedAt` as part of verification, retrying if it moved since the read, not just checking the write token. Third, `_clearPersisted()` had no error handling around its two storage calls; a rejected `chrome.storage` call there would leave `_writeQueue` itself a rejected promise, and since every future `_mergeAndPersist()`/`_clearPersisted()` call chains onto it with `.then()` and no rejection handler, that one failure would silently wedge all logging (merges and clears alike) until the service worker next restarted. Wrapped in `try`/`catch` to keep the queue alive across a failed clear, matching the resilience `_mergeAndPersist()` already had. A seventh round caught two more, both in the same function: the previous round's `clearedAt` re-check only re-filtered the incoming `entries`, not the persisted `current`/`currentFull` themselves — a worker whose earlier attempt had already written a stale pre-clear snapshot to storage (see the sixth round above) would, on noticing the clear and retrying, filter its own `entries` down to nothing and return early without ever purging that already-written stale snapshot, so Clear could still end up undone. Every attempt now re-filters the persisted buffers against `clearedAt` too, and writes the cleaned result even when the incoming batch itself has nothing new to add. Separately, a corrupt persisted buffer (malformed JSON) threw on every one of the 5 retry attempts without ever being recovered, so `_flushNow()` requeued the same unpersistable batch indefinitely, retrying roughly every 1.5s forever and blocking every later log entry from ever being persisted either. Each buffer is now parsed defensively and replaced with an empty array if corrupt, the same recovery the old (now-removed) buffer loader already had. An eighth round then caught that Clear's own final step could still be the one undoing correctness, from the opposite direction of every round before it: `_clearPersisted()` wrote the `clearedAt` cutoff, then unconditionally `remove()`d the buffer keys outright — if another worker's merge landed, filtered against that same cutoff, and successfully persisted its (legitimately newer) batch in the gap between those two steps, the unconditional `remove()` deleted that already-verified batch anyway, since a raw `remove()` has no way to tell "old" apart from "just landed". `_clearPersisted()` no longer removes the buffer keys directly at all: after writing the cutoff, it now calls `_mergeAndPersist([])`, reusing the exact same filter/write/verify/retry machinery a normal merge already goes through, so "clearing" and "merging" become the same timestamp-filtered operation and can no longer race each other in a way that loses data either direction. A ninth round then caught that the previous round's malformed-JSON recovery only handled `JSON.parse` actually throwing, not syntactically valid JSON that isn't an array (`null`, `{}`, etc., however that got into storage) — the same "corrupt buffer" failure mode from two rounds ago, just via a path the earlier fix didn't cover, with the same wedged-retries-forever consequence; `parseBuffer()` now falls back to `[]` for any non-array result too, not just an outright parse failure. That round's other finding is a genuinely different kind of issue, not a refinement of the concurrency mechanism the previous eight rounds were all narrowing down: `gsLogBufferClearedAt`, and every entry's own `ts`, both come from the wall clock, so a clock correction that moves the system time backward after a clear would make every subsequently-logged entry look older than the cutoff and have it silently (and indefinitely, until the clock catches back up) discarded by the exact same filtering this whole mechanism relies on. Deliberately left as a known, disclosed limitation rather than fixed here: replacing a wall-clock cutoff with a clock-independent generation/sequence marker is a larger, more invasive change than anything else in this pass, the failure mode (a machine's clock being corrected backward, immediately followed by "Clear log") is narrow, and the impact is limited to the debug-only log buffer, not any tab-suspend behaviour. A tenth round then caught that the previous round's unification (Clear now calls the same merge machinery as a normal write) had a gap of its own: if the `gsLogBufferClearedAt` write itself failed, the code still unconditionally went on to the purge step, which filtered against whatever cutoff was already in storage (unchanged, since the new one never landed), found nothing to purge, and reported success — so a failed Clear looked identical to a successful one from `clearLogBuffer()`'s side, and the debug page would refresh showing every old entry still there despite believing it had just been cleared. The purge now only runs when the cutoff write actually succeeded; on failure it reports `false` directly. Implementing that safely needed a small refactor: `_mergeAndPersist()`'s retry loop was pulled out into a separate `_mergeAndPersistCore()` that doesn't chain onto `_writeQueue` itself, since calling the queued `_mergeAndPersist()` wrapper reactively from inside `_clearPersisted()`'s own already-queued callback would have read `_writeQueue`'s value at whatever point that callback happened to run (by then possibly already advanced by other operations queued after it), risking a circular wait between the two steps; `_clearPersisted()` now calls the unchained core directly within its own single queued step instead. An eleventh round then caught a third variant of the same "corrupt buffer wedges retries forever" failure mode from two rounds ago, one layer deeper: even a syntactically valid array can contain a malformed *element* (`null`, a stray primitive, an object with a non-string `ts`, however it got there), which reached the `e.ts > clearedAt` comparison during filtering and threw there instead, with the same indefinite-retry consequence as an outright parse failure or a non-array top level. `parseBuffer()` now filters out anything that isn't a well-formed entry (an object with a string `ts`) after parsing, closing this specific class of corruption at the element level instead of only the top level. A twelfth round then caught that `_clearPersisted()`'s now-genuine `true`/`false` result (from the tenth round above) still never left `gsUtils.js`: `clearLogBuffer()` discarded it, `background.js`'s `clearLogs` case never set a response, and the debug page's "Clear log" button always just refreshed the log view regardless, so a failed clear (a transient storage error, or exhausted purge retries) looked identical to a successful one, with no indication the old entries were still there. `clearLogBuffer()` now returns the result instead of discarding it, `background.js` responds with `{ success }`, and "Clear log" briefly shows "clear failed" on the button (mirroring "repair favicons now"'s existing result-text pattern) instead of silently refreshing as if nothing were wrong. A thirteenth round then caught a gap in the sixth round's own async-IIFE fix: if any awaited call inside the switch threw (`performTabChecks()` failing, an unexpected manual-backup error, etc.), the detached IIFE simply rejected with nothing catching it, so `sendResponse()` never ran — since the outer listener had already returned `true` to keep the channel open, the sender was left waiting until the message port itself eventually tore down instead of promptly seeing the failure. The switch is now wrapped in `try`/`catch`, logging the error and still calling `sendResponse()` so the channel is always settled either way.
- **Battery-specific timeout (and the older "never suspend while charging" option) never actually reacted to unplugging the computer** (`background.js`, `manifest.json`, `offscreen.html`, `offscreen.js`, #252): `navigator.getBattery()` is a Window-only API and was never actually available in this MV3 service worker (a `@TODO` comment already flagged this back when "never suspend while charging" first shipped, but the surrounding code was left in place anyway), so `tgs.setCharging()` was never called and `tgs.isCharging()` always returned `undefined`. Confirmed via live testing: unplugging never updated any tab's timer, and a newly opened tab always used the AC timeout even while genuinely running on battery; the debug page's own power-source indicator (added above) still showed the correct state, since it reads `navigator.getBattery()` directly in its own page context, which is exactly what pointed at the service worker being the one with no access. Fixed properly with `chrome.offscreen`: a new hidden offscreen document (`offscreen.html`/`offscreen.js`, real Window context) reads the battery and reports charging-state changes to the service worker via a `batteryStatus` runtime message, handled in `background.js`'s existing message listener the same way the old (non-functional) in-service-worker listener tried to. `ensureOffscreenDocument()` (re)creates the document on every service worker wake if missing, since it isn't guaranteed to survive across recycles. Requires the new `offscreen` permission (silent, no runtime consent prompt or Chrome Web Store warning, unlike `downloads`/`identity`).
- **"Reload also unsuspends tabs in the background" never fired when combined with "Discard tab after suspend"** (`suspended.js`, #158): `initTab()`'s `quickInit` fast path (used for any background tab suspended while "Discard after suspend" is on) returns before ever reaching `setUnloadTabHandler`, so the `beforeunload` listener the new option depends on was never registered for those tabs; the option looked enabled but silently did nothing. `quickInit` now still registers the listener when the option is on, skipping the rest of the (unneeded, since the tab gets discarded anyway) heavy setup.
- **Suspended tabs could register a second `beforeunload` listener with a stale snapshot, racing the first on reload** (`suspended.js`, #158): `initTab()` calls `setUnloadTabHandler(tab)` on every non-quick reinit, including the one `checkQueue` triggers when it finds a suspended tab unresponsive, with no guard against calling it more than once per page. A tab reinitialised this way ended up with two `beforeunload` listeners, each closing over its own `tab` snapshot; on the actual unload both fired and wrote `STATE_UNLOADED_URL` asynchronously, so whichever storage write resolved last won, independent of which snapshot was actually correct. Surfaced by testing the new background-tab reload-to-unsuspend option above: out of 4 tabs reloaded together, the 2 that had been reinitialised by `checkQueue` failed to unsuspend while the other 2 worked, non-deterministically. `setUnloadTabHandler` now registers the listener only once per page, since the suspended.html URL is stable for the tab's whole suspended lifetime, so the first capture was always the right one.
- **Multi-tab reload could still unsuspend only a random subset of the tabs, non-deterministically** (`suspended.js`, #158): even after the dedupe fix above, the `beforeunload` handler still made ~4 sequential async `chrome.storage` round trips (a diagnostic log read, a settings lookup, then a read-modify-write for the actual flag) before writing `STATE_UNLOADED_URL`, and Chrome gives `beforeunload` no guarantee that pending async work finishes before the page is torn down. Reloading several suspended tabs together contends for the same storage IPC, so on a loaded system some of those writes lost the race and never landed, and which tabs lost was different every run. `reloadUnsuspendBackground` is now resolved once at page-init time (no time pressure there) and passed in, cutting the handler's pre-write hops from ~4 down to 1.
- **Changelog modal failed silently, with no way to diagnose why** (`gsChangelog.js`): `renderVersionChangelog()` returned `false` on every failure path (bad fetch, missing version section, exception) without ever logging anything, and `options.js` marks the version "seen" unconditionally right after calling it, so a failure permanently burns the one chance to show that version's modal, with zero trace even in a `captureLogs` report. Root-caused on a real Windows "Load unpacked" checkout: `src/CHANGELOG.md` is tracked as a symlink to the root `CHANGELOG.md`, but Git for Windows without symlink support checks it out as a 15-byte text file containing just the literal target path (`../CHANGELOG.md`) instead of a real symlink, so the fetch "succeeded" with 15 bytes of garbage, found no `## [version]` heading, and gave up without a word. Every failure path now logs a `gsUtils.warning()` with enough detail to diagnose it (HTTP status, missing section name, or, for suspiciously short responses, an explicit note that this is the known broken-symlink-on-Windows scenario, not a real changelog).
- **Debug page: live log times shown in UTC instead of the viewer's local time** (`debug.js`): `entry.ts` is stored as UTC (`new Date().toISOString()`, unambiguous no matter who reads the raw history), but the live view rendered it with a raw `substring()`, so a tester's local clock and the log timestamps could be hours apart with no indication either was UTC. The live view now renders local time; the Copy/Download report keeps the raw UTC timestamps, where lack of ambiguity across machines/timezones matters more than at-a-glance readability.
- **A tab requiring several requeues in `checkQueue` (or the suspension queue) could be killed by a stale job timeout mid-progress** (`gsTabQueue.js`): `processTab()` starts a job's timeout timer only once, on its very first execution attempt (`if (!tabDetails.hasOwnProperty('timeoutTimer'))`); `requeueTab()`, called for perfectly normal reasons like "tab still loading" or "no context yet", never touched that timer. So a job needing several requeues (common when many suspended tabs get reinitialised together, e.g. after a bulk reload) kept counting down against its original attempt's deadline, and could get killed with a false "timeout" partway through, even though each individual step was fast and it was actively making progress. Confirmed via a debug report: a burst of `checkQueue ... timeout` failures across many unrelated tabs landed almost exactly 60s (the default `jobTimeout`) after the matching burst of `initialiseSuspendedTab` calls that had queued them. `requeueTab()` now clears the stale timer so the next attempt starts a fresh timeout window, since a requeue is progress, not a hang. Resetting the timer on every requeue also removed the queue's only terminal deadline, though; a tab stuck permanently requeuing (e.g. `status` never leaving `'loading'`) would no longer time out at all, which during startup could keep `performInitialisationTabChecks()`'s `Promise.all` waiting forever, so a `MAX_REQUEUES` cap (100) now forces those through the existing exception path instead.
- **Suspended tabs could get stuck showing the raw `suspended.html#ttl=…&uri=…` placeholder, no title, no favicon, until manually reloaded** (`tgs.js`, `suspended.js`): right after a suspended tab's status flipped to `complete`, the background sent it an `initTab` message, but that page's own script (and therefore its `chrome.runtime.onMessage` listener) could still be a beat behind, especially with many suspended tabs completing in the same burst (e.g. dozens of tabs restored at browser startup). A single failed send meant `initTab()` never ran at all for that page load, so nothing (title, favicon, or the page being shown) ever got set. The existing background responsiveness check would eventually catch and reinitialise it, but that recovery pass is `setTimeout`-based and not guaranteed to survive a service worker recycle in between, so in practice a tab could stay stuck well past 10s, if it recovered at all, until manually reloaded. Two changes: the `initTab` send now retries a few times with a short delay before giving up, and `suspended.js` registers its message listener as soon as the DOM is ready instead of waiting on the full localisation chain (locale storage read, possible locale-file fetch, mascot/theme application), since that chain has no fixed upper bound under the same concurrent-startup load and could still outlast a handful of fixed retries. Still reproducible under real stress-testing (hundreds of tabs, browser-crash recovery) even with those two fixes, since the original 3×150ms=450ms retry budget wasn't generous enough for every tab in a large-enough burst. `sendInitTabMessageWithRetry()` now uses exponential backoff (`[100, 200, 400, 800, 1500, 3000]`ms, ~6s total) instead of a short fixed interval: the happy path (first attempt succeeds, the overwhelming majority of tabs) is unaffected, since added time is only ever spent on retries that have already failed once, invisibly, in the background.
- **Suspended-tab page too bright in dark mode: title/URL text and mascot artwork** (`suspended.css`, `suspended.js`, #446): reported via a comment on the KB blog post about the classic TGS artwork option, then confirmed independently by another user via email. `.gsTopBarTitle`/`.gsTopBarUrl` used `color: inherit` (full-brightness `--foreground`) since the visual redesign, noticeably brighter than before at night; now dimmed to `--muted-foreground` in dark mode only, matching the `.watermark` text that was already using it. Separately, the suspended-page mascot (`snoozy_tab`/`snoozy_tab_awake`) had no dark-mode treatment, unlike the favicon which already gets a `filter: invert(1) grayscale(1)` low-contrast pass via `.faviconWrapLowContrast`; the mascot now gets its own dimming filter (`.mascotLowContrast`, `brightness(0.7)`), toggled alongside theme/mascot updates in dark mode regardless of whether the classic TGS artwork option is on; the first pass only dimmed the legacy artwork, but the default modern mascot glares just as much and is what most users actually see.
- **Downloading a single Drive backup from the Backup page nested it inside a `tms-backups` subfolder** (`gsBackup.js`): the "Download" button next to each Drive backup entry in `backup.html` (`downloadDriveBackupAsFile`) reused `BACKUP_SUBDIR`, the same `tms-backups/` prefix used by the automatic/manual local-backup rotation system (`performLocalBackup`), but this is a one-off explicit download of a specific file, not part of that rotation (it's never added to `tmsLocalBackupIds`, so it's not tracked or cleaned up either). It now downloads straight into the browser's default Downloads location like any other single-file download, instead of silently nesting it in a subfolder meant for a different feature. Also switched `conflictAction` from `overwrite` to `uniquify`: safe inside the extension's own isolated subfolder, but risked silently clobbering an unrelated same-named file now that the download lands in the general Downloads root.
- **Legacy mascot artwork used the raw original TGS assets instead of TMS's own modified versions** (`img/legacy/`): the "Use the classic The Great Suspender artwork" option (added in 9.0.2) had every `img/legacy/` asset sourced from plain upstream The Great Suspender artwork rather than TMS 8.1.6's own re-branded set (the Marvellous "M" badge on the mascot's chest, TMS's reworked `snoozy_tab`/`snoozy_tab_awake` illustrations, etc.), most visible on the SVGs, where the wrong ~2.6 KB "_original" TGS file had been used instead of TMS's ~32 KB reworked one. Re-sourced every asset from TMS 8.1.6 (`chromeDefaultFavicon(Sml)`, `chromeDevDefaultFavicon(Sml)`, `ic_suspendy_*`, `suspendy-guy*`, `snoozy_tab*`): toolbar/action PNG icons copied as-is, illustrations re-converted to WebP (`cwebp -q 90 -m 6`), SVGs copied as-is. No code changes; `gsMascot.js`'s mapping was already correct, only the asset content was wrong.
- **"Suspend/unsuspend all tabs in this group" ignored whitelist, pinned, audible, form-input, and active-tab protections** (`tgs.js`, #133): `suspendTabGroup()` queued every tab in the clicked group with `forceLevel` 1, the same level used for an explicit single-tab "force suspend" action, which skips every protection check above `isSpecialTab()`. Since the user only actually acted on one tab in the group, the other tabs swept along with it (the active tab, a pinned tab, one mid-form-input, etc.) could be suspended without any of the protections the equivalent single-tab/selected-tabs actions respect. Now queued at `forceLevel` 2, the same level `checkTabEligibilityForSuspension()` uses for a soft/normal suspend, so those protections apply to the tabs the user didn't directly click on. Found via Codex code review. A follow-up review round caught that this fix went too far: `forceLevel` 2 unconditionally rejects the currently focused tab, so if the acted-on tab (the one clicked, or the active tab when triggered via keyboard shortcut) was itself the active tab, the group action could no longer suspend it at all — the very tab the user meant to act on. The acted-on tab now stays at `forceLevel` 1 while the rest of the group uses `forceLevel` 2, matching how the equivalent single-tab actions already treat the tab the user directly triggers versus tabs only swept along incidentally.
- **Battery-specific auto-suspend timeout stopped working on Chrome versions below 150** (`background.js`, #252): `ensureOffscreenDocument()` called `chrome.offscreen.hasDocument()` unconditionally, but that method only exists from Chrome 150 onward, while `manifest.json` still declares Chrome 110 as the minimum; on 110-149 the call threw before `createDocument()` ever ran, so the offscreen document (and therefore battery status and the timeout override) silently never worked at all on any version below 150. Added a `hasDocument` feature-check with a `self.clients.matchAll()` fallback, which is a standard `ServiceWorkerGlobalScope` API available across the whole supported range, plus a `try`/`catch` around the whole function so a future API surface change fails closed instead of throwing unhandled. Found via Codex code review.
- **"Repair favicons now" (and other async debug/settings actions) could report failure even after completing successfully** (`background.js`, #449): `messageRequestListener` was declared `async`, so it always returned a `Promise` from `chrome.runtime.onMessage.addListener`'s perspective instead of the literal `true` Chrome requires to keep a message channel open for a later `sendResponse()`; any case that `await`ed something before responding (`repairFavicons` in particular, since it awaits `gsSession.performTabChecks()` and returns real counts) could have its response silently dropped once the channel closed early. The listener is now a synchronous function that runs its body in an internal async IIFE and returns `true` immediately, so the channel stays open for the actual `sendResponse()` call regardless of how long the awaited work takes. Found via Codex code review.
- **Battery-specific timeout became impossible to configure once the AC timeout was set to "Never"** (`options.html`, #252): the new battery-timeout row shared the `.autoSuspendOption` class with the AC-timeout-dependent options, so `setAutoSuspendOptionsVisibility(false)` (triggered whenever AC timeout = "Never") hid it along with them — even though `checkTabEligibilityForSuspension()`'s effective-timeout logic explicitly supports a battery timeout overriding a disabled AC timeout. The row no longer carries that class, so it stays visible and configurable independently of the AC timeout's value. Found via Codex code review.
- **"Reload also unsuspends tabs in the background" didn't take effect on already-suspended tabs when toggled** (`suspended.js`, #158): `setUnloadTabHandler()` closed over the option's value as it stood at the tab's own `initTab()` time; toggling the option afterward had no effect on tabs already suspended and loaded, since nothing about the option change ever reached those pages. The captured value is now mutable module state, kept in sync via a `chrome.storage.onChanged` listener on the `gsSettings` blob gsStorage persists all options under, so a toggle in Options applies immediately to every open suspended page without adding any `chrome.storage` read inside the time-sensitive `beforeunload` handler itself. Also fixed the same closure-over-initial-value gap in `initTab()`'s `quickInit` fast path, which previously only registered the listener at all when the option was already on at that moment, so enabling it later never added a handler for tabs that took that path. Found via Codex code review.
